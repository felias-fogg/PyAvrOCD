Observations

  1. structureThe levels are separated in different ways. Inside pyedbglib, L1 and L0 are one inheritance chain: Avr8Protocol is-a Jtagice3Protocol is-a … is-a DapWrapper, which holds the transport. In pyavrocd's own mkII code, the levels are separate objects joined by composition: backend → protocol → transport.
  2. structureThe two stacks are not equally deep. EDBG has a level L2 from pymcuprog (NVM provider → target → Avr8Protocol), and pyavrocd's X… classes extend it. The mkII path has no L2: Jtag2Backend builds the device descriptor and context itself and calls Jtag2Protocol directly.
  3. MROEdbgBackend's MRO is EdbgBackend → AvrSession → DebugBackend → ABC → AvrDebugger. A method that pymcuprog's AvrDebugger defines is used only when none of pyavrocd's own classes defines the same name.
  4. signalsThe signal guard sits at different levels. For EDBG it wraps the two pyedbglib L0 methods DapWrapper.dap_command_response and AvrCommand.avr_command_response. For mkII and dw-link it sits one level higher, in Jtag2Protocol.command(), around a command together with its response. Jtag2Backend.guard_transactions() therefore does nothing.
  5. typingThe two mkII transports have no common base class. They share flush(), write_frame(), read_frame() and close() only by duck typing; set_baudrate() exists only on the serial one. That is why DwlinkBackend needs # type: ignore[assignment] on transport and protocol. A typing.Protocol for the transport would remove the ignores.
  6. unusedXXmegaAvrTarget is not referenced outside xavr8target.py. The ToolSpec registry (TOOLS, register_tool(), discover_probes()) is never filled; main.py chooses the backend with EDBG_TOOLS and JTAG2_TOOLS. The registry is meant for the time when a fourth probe family arrives.
